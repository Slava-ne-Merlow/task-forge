# План разработки TaskForge

## Цель проекта

TaskForge — веб-приложение для управления задачами внутри команды разработчиков.
Продукт решает проблему координации работы: кто что делает, сколько времени уходит и насколько задача близка к завершению.

Ключевые принципы: ролевая модель (Owner → Lead → Developer), прозрачная история работы по каждой задаче и отслеживание затраченного времени.

## Пользовательские сценарии

1. **Регистрация и вступление в команду**
   — Пользователь регистрируется сам или переходит по invite-ссылке от Owner/Lead.
   После принятия инвайта он автоматически добавляется в команду с ролью Developer.

2. **Создание проекта и задач**
   — Owner создаёт команду и проект. Lead создаёт задачи, назначает исполнителей и дедлайны.
   Developer берёт задачу на себя (claim), переводит в In Progress и логирует часы работы.

3. **Работа с канбан-доской**
   — Участник открывает доску проекта, видит задачи по статусам (Todo / In Progress / Review / Done),
   фильтрует по приоритету или исполнителю, сортирует по дедлайну.
   Нажимает на карточку — проваливается в детали задачи с историей активности.

4. **Ревью и закрытие задачи**
   — Разработчик переводит задачу в Review. Lead или Owner видят задачи в очереди ревью,
   апрувят (→ Done) или отклоняют с комментарием (→ In Progress).
   Весь цикл фиксируется в истории задачи с временными метками.

## Этапы разработки

| Срок | Задача |
|------|--------|
| 1–2 неделя (апрель) | Проектирование: роли, модели данных, UX-концепция |
| 3–4 неделя (апрель) | Backend: FastAPI + SQLite, auth, teams, invitations |
| 1–2 неделя (май) | Frontend core: авторизация, команды, инвайты, NgRx Signal Store |
| 3 неделя (май) | Проекты и Kanban-доска, фильтрация, сортировка |
| 4 неделя (май) | Задачи: work log, approve/reject, task detail |
| 5 неделя (май) | CI/CD, деплой на VPS, линтеры, тесты |
| 6 неделя (май) | Документация, Lighthouse, финальные правки |

## Риски и способы снижения

1. **Несовместимость TaigaUI 5 с Angular 21**
   → Риск: breaking changes в API компонентов между мажорными версиями.
   → Снижение: заранее проверить peer dependencies, держать `@angular-eslint` в синхронизации с версией Angular, при необходимости — экстрактить structural CSS из compiled MJS.

2. **Сложность zoneless + NgRx Signals в тестах**
   → Риск: Angular TestBed в zoneless режиме требует явного `provideZonelessChangeDetection()`, компонентные тесты с TaigaUI не компилируются в виде raw vitest.
   → Снижение: тестировать на уровне сервисов, guards и store-логики; компонентные тесты покрывать Playwright.

3. **Безопасность invite-ссылок**
   → Риск: одноразовые ссылки могут быть перехвачены.
   → Снижение: токены — UUID v4, одноразовые (флаг `used_at`), TTL 72 часа, HTTPS в проде.

4. **Производительность при большом числе задач**
   → Риск: N+1 запросы к БД при загрузке досок.
   → Снижение: `joinedload` на всех критичных запросах, кэширование в NgRx Signal Store на фронте.

5. **Потеря данных при деплое**
   → Риск: `rsync --delete` может удалить SQLite базу при деплое.
   → Снижение: исключить `*.db` из rsync-зеркала через `--exclude`; в будущем — миграция на PostgreSQL.
